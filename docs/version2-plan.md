# MelodyVision Version 2 改造计划

## 1. 基线与目标

- Version 1 稳定标签：`version1.0`
- Version 1 基线提交：`f1def7f94e31641087677e3b59538ae5abe21231`
- Version 2 开发分支：`codex/version2-co-creation`
- 当前状态：`V2-09` 已完成，下一项为 `V2-10`

Version 2 将 MelodyVision 从线性的“音频分析、音乐家评论、视觉参数选择、生图”流程，改造为以用户参与为核心的对话式音乐视觉共创系统。

最终产品路径缩减为四步：

```text
音乐输入 -> 选择音乐家 -> 共创聆听室 -> 画作呈现
```

旧第四页的视觉参数选择将被移除。风格、色彩、构图、材质等画面信息由音乐家对话和用户表达逐步形成。

## 2. 核心数据结构

Version 2 以三份结构化数据作为模块之间的稳定接口：

- `MusicProfile`：音乐节奏、调性、动态、结构、音色和语义分析，并记录置信度、来源和分析器版本。
- `ConversationState`：选中的音乐家、共享上下文、用户回合、当前发言权和对话阶段。
- `VisualBrief`：主体、空间、运动、材质、色彩、光线、情绪和个人意义，以及每项内容的来源映射。

`sessionStorage` 只用于前端缓存，不再作为完整流程的唯一数据来源。

## 3. 多智能体架构

### 3.1 三级结构

```text
控制层：对话状态机 + 隐形主持智能体
对话层：用户选择的 1-4 位音乐家智能体
记录层：后台视觉记录智能体
```

对话完成后，由独立的 Prompt Composer 和校验器读取 `MusicProfile` 与 `VisualBrief`，生成最终生图 Prompt。音频分析器属于确定性分析服务，不作为聊天智能体。

### 3.2 音乐家按需加载

系统维护一个通用音乐家智能体运行器和 10 份音乐家人格配置，不创建 10 个长期运行的模型服务。

用户选择哪位音乐家，就为当前会话加载对应的人格、聆听倾向和角色记忆。单次会话最多激活 4 位音乐家。不同角色可以共用同一个底层大模型，但提示词、私有记忆和输出目标相互隔离。

### 3.3 共享上下文

- 第一轮允许每位已选音乐家独立形成初始听法，避免被第一位发言者锚定。
- 对外展示时优先选择观点差异最大的 1-2 位音乐家。
- 后续音乐家可以看到共同对话、用户表达和自己的历史发言。
- 音乐家可以同意、补充或反驳彼此，但不能无限自由聊天。

### 3.4 主持人的可见形式

主持人不作为第五位人物出现：

- 不显示头像。
- 不使用人物评论气泡。
- 不要求用户与主持人建立独立对话关系。
- 只通过舞台字幕进行简短过渡、总结和提问。

用户在体验上始终是与所选音乐家交流。主持人只是不可见的节奏控制者。

### 3.5 用户进场规则

用户参与时机不能只依赖主持智能体自行判断，必须由对话状态机硬性限制：

1. 用户进入共创聆听室后，最多连续展示两段音乐家发言。
2. 两段发言结束后，必须立即进入用户回合。
3. 用户每次表达后，最多允许 1-2 位音乐家回应。
4. 音乐家之间最多进行一次直接交锋，之后必须邀请用户。
5. 默认最多进行三轮用户参与；信息充分时可以提前结束。
6. 用户可以随时打断并输入自己的听感。
7. 用户可以随时选择提前生成，不强制完成所有轮次。
8. 主持字幕每次只做一句总结或提出一个问题，不发表长篇评论。

不同选择人数的默认节奏：

- 1 位：音乐家发言，然后立即邀请用户。
- 2 位：两位给出不同听法，然后邀请用户。
- 3-4 位：先展示两位差异较大的听法；用户表达后，再由其他音乐家补充。

### 3.6 视觉记录智能体

视觉记录智能体不参与聊天，也不显示人物形象。它在每个完整回合后更新 `VisualBrief`，并为每个画面元素记录来源：

- 音乐分析证据
- 音乐家观点
- 用户原始表达

音频分析层不直接输出具体视觉意象，避免在用户和音乐家参与之前预先决定画面。

## 4. Version 2 改造清单

- [x] `V2-00` 建立 Version 2 开发分支
  - 从 `version1.0` 稳定基线创建独立分支。
  - 将完整改造清单和架构结论写入项目文档。
  - 验收：Version 1 可随时恢复，Version 2 拥有独立开发记录。

- [x] `V2-01` 定义三份核心数据格式
  - 建立 `MusicProfile`、`ConversationState`、`VisualBrief`。
  - 验收：音频、对话、视觉意图使用统一结构，并记录版本和来源。

- [x] `V2-02` 制作新音频分析原型
  - 建立 `librosa + CLAP` Python 分析服务。
  - 先分析现有示例音乐，不替换正式流程。
  - 验收：输出节奏、调性、动态、真实段落、情绪、乐器、质感和置信度。
  - 结果：8 首示例均可完成分析；CLAP 语义存在可复现误判，已作为 `V2-03` 的重点验证项，当前不得作为确定事实使用。

- [x] `V2-03` 对比新旧音频分析
  - 使用相同音乐比较 Meyda 与新方案。
  - 保存分析耗时、结构化结果和人工评价。
  - 验收：确认新方案改善音乐描述后再进入正式接入。
  - 结果：信号、结构和证据层通过；CLAP 流派与乐器未通过事实级使用门槛，V2-04 仅受控接入候选语义并优先采用已知 catalog metadata。

- [x] `V2-04` 正式接入新音频分析
  - 示例、搜索和上传统一调用 Python 服务。
  - Meyda 只保留给水晶、波形和实时律动动画。
  - 验收：MP3、WAV、FLAC、OGG 均可分析，服务异常时有降级方案。
  - 结果：Next 代理、CLAP 启动预热、完整 `MusicProfile`、兼容视图和 `meyda-degraded` 路径均已接入；已知 metadata 优先，CLAP 流派与乐器从事实上下文中屏蔽。

- [x] `V2-05` 重写音乐家人格系统
  - 建立通用音乐家智能体运行器和 10 份人物配置。
  - 弱化单字标签、固定口头禅和套路示例。
  - 验收：音乐家能提出音乐证据、个人解释、画面想象和用户问题，人物有差异但不脸谱化。
  - 结果：UI 角色数据与 Agent 人格配置已分离；10 位音乐家按需加载，共用统一输出契约、显示清理和一次质量重试；真实模型抽查已呈现不同听法，评论不再展示时间戳、BPM 或固定口号。

- [x] `V2-06` 建立主持与对话状态机
  - 主持智能体选择发言者、控制轮次、避免重复并邀请用户。
  - 将用户进场规则实现为程序约束。
  - 验收：最多两段音乐家发言后必须进入用户回合，用户可以随时打断。
  - 结果：主持 Agent 只在状态机允许的候选中选择 1-2 位音乐家并提出用户问题；舞台过渡字幕由程序生成，避免主持成为第五位评论者；首轮状态已通过 `/api/conversation/start` 接入选择页并保存，越权输出和模型失败均有确定性降级。

- [x] `V2-07` 实现共享上下文和真实流式输出
  - 音乐家读取共同对话、用户表达和自己的历史观点。
  - 使用服务端真实流式输出替代前端逐字模拟。
  - 验收：音乐家不会串角色，可以回应彼此，刷新页面后对话可以恢复。
  - 结果：第三页已改为状态机驱动的 NDJSON 服务端流；每位音乐家读取最近共同消息和自身历史，用户可中断并触发新一轮；运行时校验阻止伪造轮次，真实模型提示词注入测试未发生串角色，完整消息可在同一标签页刷新后恢复。

- [x] `V2-08` 建立后台视觉记录智能体
  - 每轮结束后更新 `VisualBrief`。
  - 保存主体、空间、运动、材质、色彩、光线和个人意义的来源映射。
  - 验收：所有核心画面元素均能追溯到音乐、音乐家或用户。
  - 结果：后台 Visual Scribe 已按完整回合更新版本化 Brief；confirmed、conflicted、音乐单独转译和已确认字段修改均有程序校验；未知来源触发一次修复后安全回退，每个有效字段均保存消息原文或音乐分析引用。

- [x] `V2-09` 重做第三页共创聆听室
  - 用户与音乐家围绕水晶共同聆听。
  - 主持人只以舞台字幕出现。
  - `VisualBrief` 以轻量方式逐步显现。
  - 验收：用户不会把主持人视为第五个人物；1-4 位音乐家均不遮挡；字幕、气泡、输入框和水晶没有重叠。
  - 结果：第三页已接入版本化 `VisualBrief` 线索带和来源提示，用户回合会强化输入入口；1-4 位舞台均使用水晶外侧固定席位，四段长评论采用上下两行；播放器收起和展开均不改变舞台坐标，并通过 1280x720 真实会话的边界对抗检查。

- [ ] `V2-10` 改造 Prompt 与生图链路
  - Prompt Director 使用 `MusicProfile + VisualBrief + 来源映射`。
  - 从第三页直接发起生成。
  - 验收：用户表达优先，关键画面元素可追溯，生成失败可修复或重试。

- [ ] `V2-11` 删除旧第四页并改造结果页
  - 导航缩减为四步。
  - 旧 `/generate-page` 暂时保留兼容跳转。
  - 结果页增加可收起的生成依据。
  - 验收：重新生成使用同一份 `VisualBrief` 和 Prompt；重新开始才清空完整流程。

- [ ] `V2-12` 补齐实验数据、部署和安全
  - 保存音频分析、完整对话、用户回合、`VisualBrief` 版本、交互事件、生成结果和反馈。
  - 部署 Python 分析服务，并保护实验数据导出接口。
  - 验收：可导出完整研究数据；音频有清理策略；Windows 服务器可自动部署和回滚。
