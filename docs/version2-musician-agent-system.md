# Version 2 音乐家智能体系统

## 1. 目标

V2-05 将旧版“角色卡 + 固定口头禅 + 示例回答”改为“通用运行器 + 按需加载的人物配置”。目标不是让模型模仿名人腔调，而是让不同音乐家基于同一份音乐证据形成可辨认、可讨论、可转化为画面的不同听法。

本阶段仍是单轮评论，不实现音乐家之间的共享上下文、主持调度或多轮状态机；这些能力分别属于 V2-06 和 V2-07。

## 2. 运行结构

```text
characterId + MusicProfile 兼容视图 + userNote
                    |
                    v
           按需加载人物配置
                    |
                    v
          通用音乐家智能体运行器
          - 组装统一任务约束
          - 调用底层大模型
          - 清理显示文本
          - 最多一次质量重试
                    |
                    v
 comment + model + profileVersion + attempts + usage
```

系统维护 10 份静态人物配置，但不会创建 10 个常驻模型服务。每次请求只根据 `characterId` 加载一份配置，并使用同一个底层模型调用入口。

## 3. 人物配置

每位音乐家的配置包含：

- `identityContext`：与其创作和聆听经验有关的身份背景。
- `listeningLenses`：至少三个可切换的听觉关注点，而非单一标签。
- `interpretiveTensions`：人物内部可以共存的矛盾，避免单线人格。
- `visualSensibilities`：对空间、运动、材质和光线的敏感方向，不预设具体画风。
- `conversationalStyle`：语气、节奏和邀请用户参与的方式。
- `avoidPatterns`：至少四条反脸谱化约束。
- `temperature`：该人物的生成自由度。

页面使用的姓名、年代、标签和简短关注说明仍保留在 `lib/characters`。模型人格配置独立放在 `lib/agents/musicians`，避免 UI 数据再次与提示词耦合。

## 4. 单轮输出契约

每次评论必须同时完成四件事：

1. 用自然听觉语言指出可以从音乐证据中听到的现象。
2. 给出该音乐家独特但非唯一正确的解释。
3. 提出可绘制的空间、运动、材质或光线想象，但不指定画风。
4. 用一个简短开放问题把发言权交给用户。

默认输出为 90-180 个中文字符、3-4 句。评论不得直接展示 BPM、秒数、时间戳、算法字段或分析术语，也不得使用标题、列表、角色署名、固定口号和示例答案。

用户听感存在时，它是需要回应的共同创作材料，不是附加备注。音频分析中的候选情绪、风格和乐器只能作为低置信度线索，音乐家不得把它们写成确定事实。

## 5. 质量与兼容性

运行器会清理角色前缀、Markdown 标题、项目符号、BPM 和时间戳。若输出为空、只有省略号、过短或没有向用户提出问题，系统会在同一人物配置下重试一次；连续两次不合格时返回失败，交由现有页面的部分失败机制处理。

`/api/comment` 保留旧前端依赖的 `characterId`、`characterName`、`comment` 和 `model` 字段，并新增：

- `agentProfileVersion`
- `attempts`
- `usage`

这使现有页面可以继续工作，同时为后续实验记录人格版本和生成稳定性。

## 6. 验证范围

- 10 位可选择音乐家均有且只有一份完整配置。
- 配置中不包含旧版固定口头禅。
- 通用提示词明确要求音乐证据、人物解释、画面想象和用户问题。
- 显示文本会移除时间戳、BPM 和角色格式。
- 空输出会触发一次重试。
- 已使用真实模型抽查伯牙、阿姆斯特朗和贝多芬，三者在关注点和表达方向上存在差异；贝多芬首次返回省略号的情况已由质量重试机制覆盖。

## 7. 下一步边界

V2-06 将在这套按需加载机制之上增加确定性的对话状态机和隐形主持智能体。主持层负责选择发言者和强制让出用户回合，但不修改本阶段的人物配置，也不把多个音乐家合并成一个统一角色。
