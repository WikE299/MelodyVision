# Version 2 主持与对话状态机

## 1. 目标与边界

V2-06 将 `ConversationState` 从数据契约变成可执行的轮次引擎，并增加一个不具有人物形象的主持智能体。核心原则是：模型可以建议，程序决定权限。

本阶段不实现音乐家共享上下文、基于用户表达生成后续回复或服务端真实流式输出，这些属于 V2-07；也不重做第三页舞台布局，这属于 V2-09。

## 2. 两层控制

```text
主持智能体
- 阅读候选音乐家的准备摘要
- 从允许候选中选择 1-2 位
- 生成一句邀请用户参与的问题
             |
             v
确定性状态机
- 校验人物是否已被用户选择
- 限制连续音乐家消息数量
- 拒绝越权或重复发言
- 强制交还用户回合
- 记录主持字幕、用户轮次和发言次数
```

主持模型不能直接修改 `ConversationState`。模型输出只有通过候选人物、人数和状态校验后，才能由 `scheduleMusicianTurn` 写入状态；无效 JSON、越权人物或模型调用失败都会使用确定性降级计划。

## 3. 状态机操作

`lib/conversation/state-machine.ts` 提供以下操作：

- `createConversationState`：创建 1-4 位音乐家的会话和独立记忆计数。
- `scheduleMusicianTurn`：接收主持计划并锁定本轮发言者。
- `recordMusicianMessage`：记录一段音乐家发言，完成本轮后自动交还用户。
- `recordUserMessage`：记录用户表达、增加用户轮次并重置连续音乐家计数。
- `requestUserTurn`：用户随时打断当前音乐家回合。
- `requestGeneration`：允许用户提前结束对话进入生成。

默认规则由既有的 `DEFAULT_CONVERSATION_TURN_POLICY` 执行：

- 音乐家最多连续发言两段。
- 单次回应最多两位音乐家。
- 最多三轮用户参与。
- 用户可以随时打断。
- 用户可以提前生成。

第三轮用户表达后，系统允许最后一轮音乐家回应；回应完成即进入 `ready-to-generate`。此后用户仍可补充文字，但不会再次开启音乐家回合。

## 4. 主持智能体

主持智能体只负责两项模型判断：

1. 在状态机给出的候选中选择下一位或两位音乐家。
2. 生成一句不替用户作答的参与邀请。

发言前的舞台字幕由程序根据最终通过校验的姓名生成，例如：

```text
先听听伯牙和贝多芬看到的不同方向。
```

这样可以避免主持模型自己解释音乐、虚构乐器或变成第五位评论者。主持消息统一使用 `facilitator + stage-subtitle`，没有头像和人物气泡。

发言公平性采用可验证规则：优先尚未发言或公开发言次数更少的音乐家；只要还有未出现的人物，就不会立即重复上一轮人物。

## 5. 当前产品接入

`POST /api/conversation/start` 接收：

- `sessionId`
- `musicProfileId`
- `selectedMusicianIds`
- `preparedSummaries`

接口创建会话、运行主持智能体并返回已经排好首轮发言者的 `ConversationState`。选择页在进入第三页前调用该接口，将 `conversationState` 和 `facilitatorPlan` 写入 `sessionStorage`。

为保证 Version 1 主流程仍可运行，主持初始化失败不会阻断进入第三页。V2-07 接入后，第三页将以 `ConversationState` 作为唯一轮次来源，并移除当前的自由点击评论逻辑。

## 6. 验证

- 1 位音乐家只发言一次就邀请用户。
- 4 位音乐家首轮最多激活 2 位，第三位直接发言会被拒绝。
- 用户可以中断尚未完成的音乐家回合。
- 后续优先选择发言次数更少且未在上一轮出现的人物。
- 越权人物、超过人数或无效主持 JSON 会降级为确定性计划。
- 三轮用户参与后，最后一轮回应完成即进入可生成状态。
- 真实模型测试成功选择两位允许人物；舞台字幕由程序生成，主持只输出用户邀请。
